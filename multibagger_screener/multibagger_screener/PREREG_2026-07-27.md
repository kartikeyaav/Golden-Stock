# Pre-registration — trailing speed (P6) and slot count under equity sizing (P5b)

**Written 2026-07-27, BEFORE either matrix was run.** Thresholds, cells and
reading rules below are fixed. This file is committed before the run so the
commit history proves the order. Same discipline as the 13 previously rejected
overlays: a criterion chosen after seeing the output is not a criterion.

Window, universe, costs and entries are IDENTICAL to the canonical baseline
(`SZ2_B_equity_cap15_r1.25`): 2023-08 → now, ~605 names, next-open fills where
stated, equity-basis sizing, risk 1.25%, value cap 15%. **Entries are not
touched by either test** — the evidence lock stands.

## P5 — queue ranking: NOT RUN. Killed by measurement, before implementation.

The idea (Clenow-style volatility-adjusted momentum instead of breakout volume
as the tie-break when several breakouts land the same day) was sound in
principle and is dead in this system for a reason that has nothing to do with
the ranking function:

| measurement | value |
|---|---|
| breakouts, 2023-08 → now, 605 names | 358 across 243 days |
| days with exactly ONE candidate (rank is a no-op) | 166 (68.3%) |
| largest same-day candidate count ever observed | 6 (cap is 12) |
| days where same-day candidates alone exceed the cap | 0 |
| **expected days where ranking changed which name was taken** | **8.2 in ~3 years** |

Ranking decides an entry only when `1 ≤ free slots < same-day candidates`.
Given the observed free-slot distribution and same-day counts, that is ~8
decisions over the whole window. Against per-trade R with a heavy right tail
(σ ≈ 5–8R), eight swapped decisions cannot produce a difference distinguishable
from noise — and a noisy "+0.15R improvement" from eight coin flips is exactly
the kind of result that gets adopted and then fails forward.

**A separate note the earlier reading conflated:** "the 12-slot cap binds 39% of
days" is about the portfolio being FULL (a breakout rejected outright), not
about same-day ordering. Measured here at 30% of days with zero free slots.
Those are different levers; only the second one is P5, and it is dead. The first
is P5b below.

P5 becomes worth revisiting only if the entry rate rises materially (a larger
universe, or a second entry class firing often). Recorded so it is not
rediscovered as a fresh idea.

## P5b — does the slot cap still cost anything under EQUITY-basis sizing?

### Why re-test something already rejected

Slot expansion was rejected 2026-07-11 (`sizing_matrix_report.md`): expectancy
fell monotonically 1.294 → 1.145 (16) → 0.892 (20) and CAGR fell too. **That
entire matrix ran on CASH-basis sizing** — `run_sizing_matrix.py` never sets
`size_on`, so it took the old default, which is the same defect corrected on
2026-07-12 (sizing measured off remaining cash undersized every late entry and
roughly halved the CAGR read).

The honest split of what that does and does not invalidate:

- **The expectancy drop is REAL and survives.** R per trade is scale-invariant;
  extra slots admit marginally weaker breakouts and that is a genuine finding.
  This test is not expected to overturn it, and if expectancy *rises* with more
  slots something is wrong with the run.
- **The CAGR/MAR comparison is NOT valid.** Portfolio return depends on how much
  capital is actually deployed, which is precisely what the cash-basis bug
  distorted — and distorted *unevenly across slot counts*, because spreading the
  same cash over more positions shrinks each one further. Whether trading more,
  individually-weaker breakouts at correct size beats trading fewer at correct
  size is therefore **untested**.

30% of days sit at the full cap with zero free slots, so this lever has real
statistical power — unlike P5.

### Cells

| cell | slots | sizing | note |
|---|---|---|---|
| `P5b_slots12` | 12 | equity | control; must reproduce `SZ2_B` |
| `P5b_slots16` | 16 | equity | |
| `P5b_slots20` | 20 | equity | |
| `P5b_slots08` | 8 | equity | the untested cheap cell (old HANDOFF "P4") |

Risk 1.25%, value cap 15%, all else baseline.

### Reading rules (fixed in advance)

1. **Control must reproduce.** `P5b_slots12` must match `SZ2_B` expectancy
   within ±0.05R. If it does not, the run is void — fix the harness, do not
   interpret the cells.
2. **Adopt a non-12 cell only if ALL hold:**
   - MAR (CAGR / |maxDD|) strictly improves vs the control, by ≥ 0.15;
   - maxDD stays inside **−25%** (the circuit-breaker rule) with ≥ 3pp margin;
   - the P2 chop cohort does not get materially worse (≥ −0.05R vs control);
   - expectancy does not fall below **+0.80R** in absolute terms — below that
     the per-trade edge is too thin to survive live slippage regardless of what
     the portfolio arithmetic says.
3. **Expectancy falling with more slots is EXPECTED and is not by itself a
   rejection** — that is the whole point of separating per-trade edge from
   portfolio return. It is a rejection only via rule 2's floor.
4. Survivor bias applies equally to all cells; compare cells to each other, not
   to the outside world.
5. One window, in-sample. A pass here authorizes **nothing live** — it makes the
   cell a candidate for a walk-forward split, no more.

## P6 — trailing speed on the trading lot

### Why

The trading lot trails the 50-DMA after taking its partial.
[Qullamaggie](https://qullamaggie.com/my-3-timeless-setups-that-have-made-me-tens-of-millions/)
trails the 10/20-DMA on comparable breakout setups. The 2026-07-27 hold-time
work sharpens the question from the other end: the **core** lot carries this
strategy (91% of profits historically; entries held 90d+ produce +200R while
everything shorter loses 45R), so the trading lot's job is arguably to bank
quickly and cheaply rather than to ride. A faster trail may raise realised R on
the half of the position that was never going to become the multibagger.

**The core lot is NOT touched.** It keeps its weekly-close-below-30-week-MA
rule. That rule is what let the winners run, and F1/F2 both showed that touching
core-lot behaviour destroys the edge.

### Cells

| cell | trading-lot trail | note |
|---|---|---|
| `P6_trail50` | 50-DMA | control; must reproduce `SZ2_B` |
| `P6_trail20` | 20-DMA | Qullamaggie-fast |
| `P6_trail10` | 10-DMA | fastest |
| `P6_trail30` | 30-DMA | intermediate, to expose dose-response |

### Reading rules (fixed in advance)

1. **Control must reproduce** `SZ2_B` within ±0.05R, else void.
2. **Adopt a faster trail only if ALL hold:**
   - blended expectancy strictly improves by ≥ **0.10R** vs control;
   - the **core lot's** R is unchanged within ±0.02R — if it moves, the cells
     are not isolating what they claim to and the run is void;
   - MAR does not fall;
   - the P2 chop cohort does not get worse by more than 0.05R.
3. **Dose-response is required.** A lone winner at 20 with 10 and 30 both worse
   is noise, not an effect. Adoption needs the ordering to be monotone in trail
   speed across at least three cells — the same standard that killed the
   fundamental-gate and sector-heat overlays (both showed clean monotone
   dose-response in the *wrong* direction, which is what made them credible
   rejections).
4. A faster trail mechanically raises turnover and therefore cost sensitivity;
   costs are already applied, but if a winning cell's margin is under 0.15R it
   is reported as **inconclusive**, not adopted.
5. One window, in-sample. A pass authorizes a walk-forward test, nothing live.

## What a null result means

Both tests are expected, on the prior set by 13 previous rejections, to fail.
That is fine and is the point: the value of running them is that the questions
stop being open, not that something gets adopted. A null result is written into
`VALIDATION_REPORT.md` with the same weight as a positive one.
